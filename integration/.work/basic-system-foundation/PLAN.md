## 현재 상태

- `project.godot`은 Godot 4.7과 GL Compatibility를 지정하며 메인 씬은 `app/bootstrap/app_root.tscn`이다. 현재 플레이 목업은 2D로 전환했다.
- 앱 루트, 중앙 화면 경로 설정, 단일 내비게이터와 6개 독립 화면 씬이 구현됐다.
- 이전 임시 시작 씬 `example_2d.tscn`은 2026-07-28 사용자 요청으로 삭제했으며 현재 시작 씬은 `app/bootstrap/app_root.tscn`만 사용한다.
- Web 프리셋과 `deploy` 브랜치용 GitHub Pages 워크플로가 있다. Godot 4.7.1 Web 템플릿 설치와 실제 내보내기·Chromium 로드가 완료됐다.
- 별도 충돌 문서 동기화 초안은 `pinball/objects/.work/collision-system-doc-sync/PLAN.md`에 있으며 충돌 단계에서 통합한다.
- Godot 4.7.1 프로젝트 스캔, 화면 6개×3회 전환 스모크, Web export, WebAssembly·PCK HTTP 200과 브라우저 한 주기 전환은 통과했다.
- 승인된 Pretendard Regular와 공용 Theme를 적용해 Web 한국어 가독성 버그를 수정했고 Chromium에서 여섯 화면을 재검증했다.
- 화면과 독립적인 런·스테이지·웨이브 진행 모델을 구현했으며 스테이지 수와 일반 웨이브 수를 `.tres` 설정으로 이동했다.
- 레퍼런스를 근사한 기본 58° 2D 목업과 `BoardViewConfig`를 추가했다. 이는 3단계의 보드 경계·앵커 전체 구현이 아니라 승인된 차원·설정 정책을 현재 씬에 적용한 선행 보완이다.
- 정규화 보드 평면의 볼록 다각형 경계와 발사·드레인·범퍼·플리퍼·유물 슬롯 앵커를 `BoardLayoutConfig`로 분리하고 현재 2D 목업이 같은 데이터를 투영·조립하게 했다.

## 구현 방향

- 최종 그래픽 차원은 미확정으로 유지한다. 플레이 규칙, 보드 데이터와 상태는 노드 차원에 의존하지 않고 2D·3D 어댑터가 같은 계약과 설정을 소비한다.
- 현재 목업은 2D 어댑터만 구현한다. 3D 어댑터와 런타임 토글은 최종 방향 승인 후 별도 단계로 구현한다.
- 메인 로비·스테이지 선택·보상·결과는 `Control`, 웨이브·보스의 현재 플레이 목업은 `Node2D` 씬으로 분리한다.
- 앱 조립, 도메인 진행, 핀볼 물리, 스테이지 데이터, 유물, 보상과 UI의 소유권을 기존 폴더 경계대로 유지한다.
- 보드 형상, 범퍼·플리퍼·발사·드레인·유물 슬롯 위치와 모든 조정 수치는 `Resource` 또는 내보내기 속성으로 관리한다.
- 단일 기능 값은 해당 기능 설정에, 둘 이상의 기능이 실제로 공유하는 단위·계약만 `shared/`에 둔다.
- 임시 리소스는 교체 가능한 장면·재질·메시 참조로 주입하고 게임 규칙 코드에 외형을 결합하지 않는다.
- 각 단계의 조정값은 검증 가능한 `.tres` 설정으로 유지하고, 11단계 통합 후반부에 편집기·디버그 실행 전용 `개발자 모드`를 추가해 앞선 단계의 설정 복제·실시간 적용·검증·저장을 한 화면에서 수행한다. 출시 빌드에서는 기본 비활성화한다.
- `.tres`에 저장되는 내부 속성명과 GDScript 변수명은 영문으로 동일하게 유지하되, Godot 인스펙터와 개발자 모드에는 승인된 한국어 표시 이름·설명·단위·범위를 제공한다. 기존 1~3단계 설정도 같은 표시 규칙으로 보완한다.
- 단계별 검증은 Godot 프로젝트 스캔, 자동 시나리오와 Desktop 실행을 기본으로 한다. Web export·Chromium 검증은 12단계 최종 Web QA 또는 사용자의 명시 요청 때만 수행한다.

- 3B는 기존 3A 데이터를 되돌리지 않고 확장하는 기능 변경으로 분류한다. 관련 `stages/boards/SPEC.md`, 구현과 QA는 사용자 승인 후에만 갱신한다.

## 3B 기획자용 보드 제작 도구 계획

- 변경 유형: `stages/boards`, `stages/waves`, `pinball/objects`, `pinball/flippers`, `relics`에 걸친 전역 기능 변경
- 사용자 목표: Godot 또는 GDScript를 모르는 기획자가 2D 화면에서 마우스로 보드를 만들고 재사용 오브젝트를 연결한 뒤 웨이브에서 바로 확인한다.
- 편집 화면 표준 용어: `보드 템플릿`, `보드 외곽선`, `배치 지점`, `웨이브 배치`, `오브젝트 원형`, `2D 디자인`, `유물 배치 지점`, `발사 지점`
- 외부 산출물: 구현·독립 QA 뒤 사용자 지정 Confluence `웨이브 보드 커스텀 가이드 문서` 페이지 `12288002`를 기존 내용 보존 방식으로 갱신한다. 현재 페이지 본문은 비어 있다.

### 권장 기획 경계

- `보드 외곽선`은 차원 독립 데이터로 저장하되, 기획자는 2D 화면의 정점 손잡이를 마우스로 이동한다.
- `배치 지점`은 위치와 허용 역할만 저장하고, 웨이브별 `웨이브 배치`가 실제 `오브젝트 원형`을 연결한다.
- 오브젝트 원형에는 오브젝트 종류, 범퍼 종류와 최대 내구도처럼 게임 규칙에 필요한 값을 둔다. 현재 2D 디자인과 미래 3D 디자인 장면은 별도 표현 연결표에서 같은 원형을 사용한다.
- 범퍼·벽·일반 오브젝트와 플리퍼의 고정 배치는 웨이브 설정이 소유한다. 유물은 기존 보드 빌딩 규칙을 보존해 보드가 `유물 배치 지점`만 제공하고 실제 획득 유물은 런타임에 연결한다. 에디터 미리보기용 유물은 플레이 상태와 분리한다.
- 최대 내구도는 오브젝트 원형, 현재 내구도는 생성된 런타임 인스턴스가 소유한다. 3B는 편집·저장·조립 계약을 구현하고, 충돌에 따른 감소·파괴·복구와 초기화 정책은 6·8단계에서 문서 승인 후 연결한다.
- 보드에는 실제 공, 공 종류와 공 능력을 저장하거나 미리 배치하지 않는다. 발사 지점 표식만 남기고, 선택한 공의 런타임 생성은 4단계가 소유한다.

### 편집기 수용 기준 요약

- 별도 스크립트 실행, GDScript 수정, `.tres` 텍스트 편집과 좌표 계산 없이 모든 기본 제작 흐름을 완료한다.
- 외곽선 정점과 배치 지점은 마우스로 이동하며 변경 결과가 즉시 보인다.
- 빈 배치 지점은 유지되지만 실제 오브젝트는 생성되지 않는다. 원형을 지정하면 같은 위치에 실제 2D 디자인이 표시되고, 다른 원형으로 교체해도 지점 정보는 유지된다.
- 잘못된 오브젝트 종류, 깨진 참조, 중복 이름, 경계 밖 지점, 잘못된 외곽선과 플리퍼 수는 하단 로그에만 남기지 않고 해당 지점과 제작 도구 화면에 원인·해결 방법을 한국어로 표시한다.
- 플리퍼는 웨이브마다 1~4개이며 외곽선을 따라 끊김 없이 이동하고 외곽선 변경 뒤에도 붙어 있어야 한다.
- 공은 보드 제작 화면과 저장 데이터에서 제외하고 발사 지점만 표시한다.

### 캡처·영상과 Confluence 구성

- 캡처: 제작 도구 전체, 외곽선 전·후, 빈 지점, 범퍼 지정, 범퍼 교체, 오브젝트 원형 설정, 플리퍼 1개·4개, 잘못된 배치, 공 없는 보드, 공 선택 후 런타임 화면을 남긴다.
- 영상 1: `보드 복제 → 외곽선 드래그 → 지점 추가·이동 → 범퍼 지정·교체 → 저장 → 웨이브 확인`을 60~90초로 기록한다.
- 영상 2: `플리퍼 1→4개 → 외곽선 이동 → 5번째 거부 → 잘못된 원형 오류 → 복구`를 45~60초로 기록한다.
- Confluence 목차: 할 수 있는 일, 쉬운 용어, 5분 빠른 시작, 템플릿 복제, 외곽선 편집, 지점 추가, 지점과 실제 오브젝트 차이, 원형 설정, 범퍼·유물·일반 오브젝트 배치, 플리퍼 배치·디자인 교체, 웨이브 연결, 실행 확인, 공 제외 이유, 오류 해결, 원상 복구, 현재 범위와 QA 환경 순서로 작성한다.
- 각 조작 절에는 `어디를 여는가`, `무엇을 클릭하는가`, `정상 화면은 무엇인가`, `잘못됐을 때 어떻게 되돌리는가`를 문장으로 적는다. 내부 파일명과 코드 용어는 접힌 개발 참고에만 둔다.

### 제외 범위와 중단 조건

- 3B는 보드 제작·데이터 저장·2D 조립을 완성하지만 공 발사 물리, 플리퍼 작동 물리, 범퍼 충돌·내구도 감소, 유물 획득·실제 배치·발동은 각각 기존 4·5·6·8단계에서 구현한다.
- 최종 아트와 3D 어댑터는 포함하지 않는다. 현재는 교체 가능한 2D 목업 디자인으로 원형 교체를 증명한다.
- Web export·브라우저 검증은 실행하지 않고 12단계 최종 QA로 이관한다. Confluence 갱신 승인은 Web 검증 승인으로 해석하지 않는다.
- 편집 도구가 실행 취소·다시 실행, 저장 안정성 또는 기존 사용자 복제본 보존을 보장하지 못하면 다음 하위 단계로 진행하지 않는다.
- 현재 작업 트리의 `my_board_layout_config.tres`, `stages/boards/.work/`, `app/navigation/default_navigation_config.tres`와 모든 기존 변경은 사용자 작업으로 간주해 덮어쓰거나 되돌리지 않는다.

## 4단계 계획 초안 — 공 선택·조준·발사·발사 반복

- 상태: 사용자 최종 승인에 따라 구현 중
- 관련 기준: GR-01~06, GR-38~40, D-01, D-02
- 선행 보완: 보드 복제본의 표준 저장 경로와 `BoardAuthoring2D` 루트 변형 경고를 3B 수정으로 먼저 처리하고 회귀 검증한다.
- 입력 계약: `공 선택` 상태에서는 `1`·`2`·`3`이 해당 공 슬롯을 직접 선택하고 좌우 방향키가 남은 공 사이를 순환 선택한다. `Space`는 선택한 공을 확정하고 `공 조준` 상태로 이동한다. 조준 방식 설정이 `방향키`면 좌우로 각도, 상하로 세기를 조절하며 방향키를 길게 누르면 같은 방향으로 일정하게 반복 조절한다. `마우스`면 포인터 방향·거리를 사용한다. 두 방식 모두 조준 상태의 `Space`가 발사를 실행한다. 공 진행 중에는 방향키가 플리퍼 선택, `Space`가 선택된 플리퍼 작동으로 전환된다. 존재하지 않거나 이미 소모한 공 슬롯 입력은 한국어 이유와 함께 거부한다.
- 보드 계약: 한 보드의 발사 지점은 정확히 1개, 플리퍼 배치 지점은 1~4개다. 개발자 모드에서도 이 범위를 벗어난 저장은 거부한다.
- 플리퍼 입력 계약: 보드 중심과 각 플리퍼의 배치 위치를 비교해 위·아래·왼쪽·오른쪽 후보를 계산하고, 최대 4개 전체에서 각 방향키가 정확히 한 플리퍼에만 연결되도록 최소 각도 오차 조합을 선택한다. 중복 방향은 저장·조립 전에 거부하고 제작 화면에 배정된 방향을 표시한다.
- 반복 계약: `발사할 공 선택 → 공 조준 → Space 발사 → 플리퍼 선택·작동 → 낙하 → 다음 공 선택`을 반복한다. 실제 플리퍼 물리 동작은 5단계에서 연결한다.
- 종료 계약: 스코어·목표가 연결되는 7단계에서는 목표를 먼저 달성해도 현재 공의 발사를 중단하지 않는다. 낙하 뒤 최종 스코어를 목표와 비교해 클리어·다음 공·실패 중 하나를 확정한다.
- 차원 경계: `LaunchCommand`는 보드 평면 방향과 정규화 세기를 담는 커맨드로 만들고, 발사 계산 전략과 `BallPhysicsAdapter`가 현재 `RigidBody2D` 또는 미래 `RigidBody3D`로 변환한다. 4단계는 2D 어댑터와 가짜 검증 어댑터만 구현한다.

| 방향키 각도 변화량 | `2°` | 좌우 입력 1회당 조준 각도 변화 |
| 방향키 세기 변화량 | `0.05` | 상하 입력 1회당 정규화 세기 변화 |
| 기본 발사 세기 | `0.60` | 조준을 시작할 때의 정규화 세기 |
| 최소·최대 발사 속도 | 초당 보드 폭 `1.0~2.5` | 정규화 세기를 실제 초기 속도로 변환하는 범위 |
| 마우스 최대 조준 거리 | 보드 폭의 `0.35` | 최대 발사 세기가 되는 포인터 거리 |
| 조준선 길이 | 보드 폭의 `0.28` | 예상 경로를 표시하는 길이 |

- 공격력, 스코어 배수, 고유 능력과 성장 수치는 4단계 표준 공 설정에 넣지 않는다. 관련 단계의 기획 승인 뒤 별도 설정으로 연결한다.
- 목업 웨이브의 공 목록은 1~3개 범위로 승인한다. 실제 기본 개수, 공을 가져오는 준비 화면과 웨이브 전환 시 보충·초기화 세부 정책은 D-02 후속 결정으로 남긴다.

### 4단계 구현 순서

1. 공·발사·한 발사 SPEC과 설정 범위, 숫자·방향키·`Space` 상태별 입력, 두 조준 전략과 차원 독립 명령·결과 계약을 문서 우선으로 확정한다.
2. 표준 공 원형, 물리 프로필과 차원별 표현 연결 키를 구현한다.
3. `LaunchCommand`, 발사 계산 전략, `BallPhysicsAdapter`와 가짜 검증 어댑터를 구현한다.
4. 현재 2D 보드에 `RigidBody2D` 공, 외곽선 벽, 발사 지점, 드레인과 보드 밖 안전 종료를 조립한다.
5. 내부 속성명을 바꾸지 않고 기존·신규 `.tres`의 인스펙터 이름·설명·단위·범위를 한국어로 표시하는 공용 편집기 표시 계층을 추가한다.
6. 공 1~3개 선택, 마우스 조준, 세기·방향 안내와 상태별 숫자키·방향키·`Space` 입력 라우팅을 연결한다.
7. 플리퍼의 보드 상대 위치에서 위·아래·왼쪽·오른쪽 고유 방향을 배정하고 중복을 거부한다. 실제 작동 물리는 5단계까지 호출 경계만 제공한다.
8. 낙하 결과를 한 번만 확정하고 남은 공이 있으면 다음 공 선택으로 돌아가는 반복을 연결한다.
9. 계약·물리·입력·생명주기·한국어 인스펙터 자동 검증과 Desktop 수동 검증을 수행한다.
10. 구현에 참여하지 않은 QA 에이전트가 독립 검증하고, 메인 에이전트 수정 뒤 같은 항목을 재검증한다.

### 11단계 개발자 모드 편입 원칙

- 1~10단계는 내부 속성명을 바꾸지 않고 각 설정에 쉬운 한국어 표시 이름, 설명, 단위, 최소·최대값, 적용 시점과 재시작 필요 여부를 함께 정의한다. Godot 인스펙터와 개발자 모드는 같은 표시 메타데이터를 사용한다.
- 11단계 통합 후반부에 이 메타데이터를 읽는 개발자 모드를 구현한다. 범주별 검색, 현재값 수정, 유효성 검사, 실시간 적용, 복제본 저장, 다시 불러오기와 기본값 복원을 제공한다.
- 편집기·디버그 실행에서 `res://` 복제 `.tres` 저장을 지원한다. 패키징된 실행 파일처럼 `res://`가 읽기 전용이면 `user://developer_presets`에 저장하고 프로젝트로 가져올 수 있게 한다.
- 출시 빌드와 최종 Web 빌드에서는 개발자 모드를 기본 비활성화하고, 게임 불변 규칙을 위반하는 값은 개발자 모드에서도 저장·적용하지 않는다.

### Godot 에디터에서 3단계를 직접 확인하는 방법

1. Godot 4.7.1에서 `stages/boards/board_mockup_2d.tscn`을 열어 기본 58° 보드, 범퍼 5개, 플리퍼 2개, 유물 슬롯 3개와 발사·드레인 표시를 확인한다.
2. `stages/boards/default_board_layout_config.tres`를 복제하고 `anchors`에서 범퍼 하나를 이동하거나 추가한다. 기본 파일은 직접 수정하지 않는다.
3. `stages/boards/board_mockup_2d.tscn`의 `layout_config`에 복제본을 연결해 위치·개수가 즉시 달라지는지 확인한다.
4. `stages/boards/default_board_view_config.tres`도 복제하고 `view_angle_degrees`를 35°와 75°로 바꿔 모든 경계·앵커가 같은 원근으로 변하는지 비교한다.
5. 복제 레이아웃의 `launch_anchor_id`를 존재하지 않는 값으로 바꾸면 보드가 부분 조립되지 않는지 확인한다. 시험 후 씬 참조를 두 기본 `.tres`로 되돌린다.

## 미확정 사항과 가정

- 최종 2D·3D 방향은 미확정이며 현재 목업만 2D다. 보드·물리 계약과 설정은 특정 노드 차원에 결합하지 않는다.

## 중단·되돌림 조건

- 문서와 구현 경계가 충돌하거나 새 미확정 기획이 필요한 경우 해당 단계에서 중단한다.
